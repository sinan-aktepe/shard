# Shard 2.0 — Design Spec (`2.0.0-dev.1` cycle)

**Date:** 2026-06-13
**Status:** Spec — approved, unstarted.
**Supersedes (for the 2.0 line only):** the "additive-only for 1.x" constraint in `2026-06-13-b-features-roadmap.md` §2. That roadmap's per-feature *designs* still apply; this document overrides the parts that were deliberately worked around to avoid breaking the frozen 1.x API.

This is the single execution reference for the `2.0.0-dev.1` development cycle. It bundles **all core "B" features (B1–B9 + B11)** under one major version, takes the **clean (breaking) redesigns** that the additive 1.x roadmap had to defer, and ships a migration guide. **B10 (DevTools)** stays a separate future package, out of scope.

---

## 0. Why 2.0 (and what changes)

The B-features roadmap designed three features around the constraint *"the 1.x public API is frozen, so everything must be additive."* That forced workarounds:

| Feature | 1.x additive workaround | 2.0 clean design (this spec) |
|---------|-------------------------|------------------------------|
| **B1** mutation/command | a parallel `CommandState` sealed type (because adding `AsyncIdle` to `AsyncValue` breaks exhaustive switches) | **add `AsyncIdle<T>`** to `AsyncValue` and build `CommandShard` directly on `AsyncValue` — one state type, one builder |
| **B6** logout clear | write an empty string (`StateStorage` has no `delete`) | **add `StateStorage.delete(key)`** — a real per-key delete |
| **B5** persistence migration | keep the bare-payload format byte-identical by default | **always write a version envelope** (legacy-tolerant read, so upgrades keep their data) |

The 2.0 major bump opens the window to do these properly. Everything else (B3, B4, B7, B8, B9, B11) was already additive and is carried over unchanged — bundled here only so the whole next wave ships as one coherent major release.

2. **Step 1 — branch + bump.** Create `feature/2.0-dev` off the 1.2.0 commit. Bump `pubspec.yaml` → `2.0.0-dev.1`. Open a new `## 2.0.0-dev.1` section at the top of `CHANGELOG.md`. Commit this together with the planning docs as the first 2.0 commit.
3. **Steps 2…N — features.** One long-lived `feature/2.0-dev` branch; **each feature is its own TDD commit(s)**. As each lands, append a one-line entry under `## 2.0.0-dev.1`, grouped `**BREAKING CHANGE**` → `**New**` → `**Fix**`.
4. **Final step — finalize.** Compact the `## 2.0.0-dev.1` CHANGELOG section (dedupe, order BREAKING→New→Fix, tighten wording, mirror the `0.2.0` BREAKING format), write the migration guide (§5), run full verification + `flutter pub publish --dry-run`.

## 2. Cross-cutting constraints (2.0)

Same as the roadmap's §2 **except** the additive-only rule. For 2.0:

1. **Breaking changes are allowed**, but only the three named in §0 (and their direct fallout). Every break needs a `**BREAKING CHANGE**` CHANGELOG entry and a migration-guide section. Do not introduce breaks beyond those three without a new decision.
2. **Zero runtime deps.** Unchanged and non-negotiable — `dart:*` and `package:flutter/*` only. No `package:collection`, `rxdart`, etc.
3. **Doc-comment everything public** with multi-line `///` blocks + example snippets (pub.dev scores it; the codebase is consistent about it).
4. **Lifecycle discipline.** `onInit`/`dispose`/`onChange`/`onError` are `@mustCallSuper`; `emit` is `@protected`. Mixins touching `emit` must mind ordering with `StatePersistenceMixin` (which overrides `emit`/`emitForce`).
5. **Tests** use `fake_async` for timers, the in-package fakes (`FakeStateStorage`/`FakeCacheService`) for adapters, and `ShardTester` for emission sequences. No real `Future.delayed`. New tests live in the matching `test/` subdir.

## 3. Breaking redesigns (the 2.0 payoff)

### F1 — AsyncValue 2.0 core *(BREAKING; foundational; combines old B2 + AsyncIdle)*

**File:** `lib/src/state_management/async_value.dart`; widget `lib/src/widgets/async_shard_builder.dart`. **Tests:** `test/state_management/async_value_test.dart`, `test/widgets/async_shard_builder_test.dart`.

**Add the idle variant.** A new `final class AsyncIdle<T> extends AsyncValue<T>` representing "not started." `FutureShard`/`StreamShard` never enter it (they start loading); it exists so mutations (F2) can start idle.

**Add pattern-matching to the sealed base** (methods/static on a sealed base are not themselves breaking, but they must handle the new `AsyncIdle` case):

```dart
sealed class AsyncValue<T> {
  // Exhaustive handler. previousData is surfaced to loading/error so callers
  // can show stale data. idle has no data.
  R when<R>({
    required R Function() idle,
    required R Function(T? previousData) loading,
    required R Function(T data) data,
    required R Function(Object error, StackTrace? stackTrace, T? previousData) error,
  });

  // Partial handler with a fallback.
  R maybeWhen<R>({
    R Function()? idle,
    R Function(T? previousData)? loading,
    R Function(T data)? data,
    R Function(Object error, StackTrace? stackTrace, T? previousData)? error,
    required R Function() orElse,
  });

  // Transform the success value, preserving idle/loading/error (+ previousData).
  AsyncValue<R> mapData<R>(R Function(T data) transform);

  // Run f only when there is data; otherwise null.
  R? whenData<R>(R Function(T data) f);

  // Wrap a future into try/catch → AsyncData / AsyncError. Optionally carry
  // previousData onto the error.
  static Future<AsyncValue<T>> guard<T>(
    Future<T> Function() future, {
    T? previousData,
  });
}
```

**Internal switches we own must add the idle case:**
- `AsyncValue.dataOrNull` switch → `AsyncIdle<T>() => null`.
- `AsyncShardBuilder.build` switch → add an `AsyncIdle` arm, routed to a **new optional** `onIdle:` builder (defaults to the loading widget). Adding an *optional* constructor param keeps existing `AsyncShardBuilder` call sites source-compatible.

**`AsyncIdle` equality/`toString`:** match the existing variants' style (`AsyncIdle<T>()` is a value with no fields; `==` by runtime type+generic, stable `hashCode`, `toString` `'AsyncIdle<$T>()'`).

**The only user-facing break:** application code that writes its own *exhaustive* `switch (asyncValue)` over the three old variants will no longer compile (non-exhaustive). Migration: add an `AsyncIdle` case, or switch to `when`/`maybeWhen`.

**Tests:**
- `when`/`maybeWhen` route each of the four subtypes correctly and pass `previousData`; `maybeWhen` falls through to `orElse` when the matching handler is null.
- `mapData` transforms `AsyncData`; leaves `AsyncIdle`/`AsyncLoading`/`AsyncError` as the same variant with `previousData` preserved.
- `whenData` returns null for idle/loading/error.
- `guard` → `AsyncData` on success, `AsyncError` (with stack + optional `previousData`) on throw.
- `AsyncShardBuilder` renders `onIdle` when idle; defaults to loading widget when `onIdle` omitted; existing loading/data/error behavior unchanged.

### F2 — CommandShard *(builds on F1; B1)*

**File:** new `lib/src/state_management/command_shard.dart` (+ export from `state_management.dart`). **Tests:** `test/state_management/command_shard_test.dart`.

A `Shard<AsyncValue<Res>>` that runs a single async action and tracks its lifecycle as `AsyncValue`: starts `AsyncIdle`, `execute` → `AsyncLoading` → `AsyncData(result)` / `AsyncError`. Renders with `AsyncShardBuilder` (+ `onIdle`). **No separate `CommandBuilder`** — the unified `AsyncValue` is the whole point (YAGNI).

```dart
/// A [Shard] that runs a single async action and exposes its lifecycle as an
/// [AsyncValue]: [AsyncIdle] → [AsyncLoading] → [AsyncData]/[AsyncError].
/// Plugs into ShardProvider / context.read / AsyncShardBuilder like any Shard.
class CommandShard<Arg, Res> extends Shard<AsyncValue<Res>> {
  CommandShard(this._action) : super(const AsyncIdle());
  final Future<Res> Function(Arg arg) _action;

  bool get isRunning => state.isLoading;
  Res? get valueOrNull => state.dataOrNull;

  /// Runs the action. Ignored if already running (double-submit guard).
  /// Returns the result on success, null on failure.
  Future<Res?> execute(Arg arg) async {
    if (state.isLoading || isDisposed) return null;
    emit(AsyncLoading(previousData: state.dataOrNull));
    try {
      final result = await _action(arg);
      if (isDisposed) return null;
      emit(AsyncData(result));
      return result;
    } catch (e, st) {
      if (isDisposed) return null;
      addError(e, st);
      emit(AsyncError(e, st, state.dataOrNull));
      return null;
    }
  }

  /// Resets back to [AsyncIdle].
  void reset() => emit(const AsyncIdle());
}
```

**Tests:**
- `execute` emits `AsyncLoading` then `AsyncData(value)` and returns the value.
- failure path emits `AsyncError(error, …)`, returns null, and routes through `addError` (assert via `MockShardObserver`).
- second `execute` while running is ignored (double-submit guard) — `Completer`-gated action; assert the action ran once.
- `reset` returns to `AsyncIdle`.
- dispose mid-run is safe (no emit after dispose).

**Open question (decide at impl):** confirm the exact `Arg`/`Res` ergonomics for no-arg commands (`CommandShard<void, Res>` with `execute(null)` vs. a `void` convenience). Keep it minimal.

### F3 — StateStorage.delete + clearPersistence *(BREAKING; B6)*

**Files:** `lib/src/persistence/storage.dart` (interface), `lib/src/persistence/state_persistence.dart` (`clearPersistence`), `lib/src/testing/...` (`FakeStateStorage`). **Tests:** `test/persistence/state_persistence_test.dart`, `test/testing/...`.

**Add to the interface:**

```dart
abstract class StateStorage {
  Future<void> save(String key, String value);
  Future<String?> load(String key);

  /// Removes any value stored under [key]. A no-op if the key is absent.
  /// Implementations must ensure a subsequent [load] returns null.
  Future<void> delete(String key);   // NEW — breaking for implementers
}
```

`clearPersistence()` cancels the pending debounced save, then chains a real `storage.delete(key)` onto the save queue (replacing the 1.x empty-string trick). Surfaced on `PersistentShard` (inherited). Does **not** change in-memory state — document pairing with `emit(initialState)` to also reset live state.

`FakeStateStorage` implements `delete` (remove the key; `rawValue(key)` becomes null). Update the `StateStorage` doc-comment example implementation to include `delete`.

**Break:** any user `implements StateStorage` must add `delete`. Migration: implement it (`prefs.remove(key)`, `box.delete(key)`, etc.).

**Tests:**
- after `clearPersistence()`, `FakeStateStorage.rawValue(key)` is null (true delete, not `''`).
- a subsequent `loadState()` calls `onLoadComplete(null)`.
- a debounced save in flight is cancelled (no stale value written after clear) — `fake_async`; assert the key is absent at the end.

### F4 — Persistence versioning + migration *(B5)*

**Files:** `lib/src/persistence/state_persistence.dart` (`PersistenceConfig`, `enablePersistence`, `loadState`, `saveState`), `lib/src/state_management/persistent_shard.dart` (constructor params). **Tests:** `test/persistence/state_persistence_test.dart`, `test/persistence/persistent_shard_test.dart`.

```dart
enablePersistence({
  ...,
  int version = 1,
  String Function(int fromVersion, String payload)? migrate,
});
```

**Envelope format (distinctive keys to avoid collision):** `{"__shard_v": <int>, "__shard_p": "<serialized payload string>"}`.

- **Write (`saveState`):** **always** write the envelope `jsonEncode({'__shard_v': version, '__shard_p': serializer.serialize(data)})`. (Clean 2.0 behavior — uniform, version always present. This is the on-disk change vs. 1.x.)
- **Read (`loadState`):** read the raw string. Try `jsonDecode`; if it is a `Map` with both `__shard_v` and `__shard_p`, it's an envelope → `storedVersion = __shard_v`, `payload = __shard_p`. Otherwise (any bare string, including all 1.x-written data) → **legacy** → `storedVersion = 1`, `payload = rawString`. If `storedVersion < version && migrate != null`, `payload = migrate(storedVersion, payload)`. Then `serializer.deserialize(payload)`.

**Legacy tolerance is the key property:** upgrading from 1.x reads the old bare payload as v1, so **no user data is lost on upgrade**. The only break is forward-compat (2.0-written envelopes aren't readable by a 1.x downgrade) — acceptable for a major bump; note it in the migration guide.

`migrate(fromVersion, payload)` is called **once**; the user owns chaining (1→2→3 inside their function). Document clearly. `PersistentShard` forwards `version`/`migrate` into `enablePersistence`.

**Tests:**
- default (`version: 1`, no `migrate`): stored value is an envelope with `__shard_v: 1`; roundtrip works.
- loading **legacy bare data** (no envelope) with `version: 2, migrate: …` calls `migrate(1, payload)` then deserializes the migrated payload (proves upgrade path).
- `version: 2` writes an envelope; reading it back with `version: 2` does not call `migrate`.
- loading a v1 envelope with current `version: 3` calls `migrate(1, …)` once.
- `migrate` throwing routes to `onLoadError`.

## 5. Migration guide (write at finalize)

Ship `docs/superpowers/specs/2026-06-13-shard-2.0-migration.md` (and summarize in README + CHANGELOG `BREAKING CHANGE` entries). It must cover the three breaks:

1. **`AsyncValue` gained `AsyncIdle`.** Exhaustive `switch (asyncValue)` in app code needs an `AsyncIdle` case (show the before/after), or migrate to `when`. `AsyncShardBuilder` users are unaffected unless they want to handle idle (`onIdle:`).
2. **`StateStorage.delete(key)` is now required.** Any `implements StateStorage` must add it — show the SharedPreferences/Hive one-liners.
3. **Persistence on-disk format is now a version envelope.** Upgrades are safe (legacy reads still work); only a 2.0→1.x *downgrade* can't read 2.0-written data. Mention `version`/`migrate` for schema evolution.
